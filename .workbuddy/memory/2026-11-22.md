## 账号体系 / 场景口令 / 操作日志（第五轮，对应 README 待办第 7 条）

### 需求

为「切换员工场次、切换玩家场次、员工登入、管理登入」提供互相独立的凭据；管理界面里为员工建账号、每人独立密码；员工用自己的账号密码登入；对账导出与关键操作把员工账号记进日志，便于追踪。

### 设计决策

- **四类凭据分离**：玩家场次口令 `PLAYER_SESSION_PASSWORD`(8888) / 员工场次口令 `STAFF_SESSION_PASSWORD`(7777) / 员工账号密码（库内 scrypt）/ 管理员账号密码（同一张 `staff_account`，role=admin）。管理员**免**场景口令（口令约束的是员工操作边界，不是认证）。
- 登录不再有共享密码：`/api/staff-login` 收 `{username,password}`；不传 username 时按初始管理员处理（兼容老脚本，`test/helpers` 依赖这一点）。
- 初始管理员由 `ADMIN_USERNAME`/`ADMIN_PASSWORD` 引导，**只在库里没有 admin 时生效**；`ADMIN_PASSWORD` 缺省时回退 `STAFF_PASSWORD`，再回退默认 `123456`（老部署升级不至于不知道管理员密码）。`STAFF_PASSWORD` 另外补建同名员工账号 `staff`。
- 权限分档：`staff` 能操作场次/锁定/新一轮/归档补齐；`admin` 另有对账导出、账号管理、日志。服务端 `requireAdmin` 硬校验，前端隐藏只是体验。
- 会话鉴权以**账号表当前状态**为准（join `staff_account`）：停用、降级、改密即踢所有会话（`deleteStaffSessionsByUser`），不等 12 小时。

## 2026-11-22 傍晚：草稿同步已落地（实施完成）

按 Matthew 的 5 条约束实施：草稿不落库 / 不校验单双与数字一致 / 必须确认才算参赛 / 客户端 500ms debounce + 值变才发 / 断线只保最终一致。

### 实现要点

- **草稿只存内存**：`draftStore / draftSeqStore / draftPending / draftTimers / submitReceipts`，`player.odd_even` 一个字节没动 → db.js 归档、对账 CSV、命中判定零改动。草稿不推进 `version`。

## 晚：数据库切到 Supabase pooler

目标连接串：`postgresql://postgres.siuilxncmpklkpcnpimg:<PASSWORD>@aws-1-ap-south-1.pooler.supabase.com:6543/postgres`

### 决策

- **连接串只进 Fly secrets，绝不进 `fly.toml`**（后者进 git）。`fly.toml` 未改动。
- **优先级反转**：`DATABASE_URL` / `PG_URL` > `PG_HOST+PG_USER+PG_PASS`。原来拆开的 PG_* 优先，换库时残留旧 secret 会静默盖掉新连接串，是个坑。换库后要 `fly secrets unset` 那五个。
- 应用区域保持 `nrt`（东京）不动，库在 ap-south-1（孟买），跨区每条查询 +70~100ms；用户明确选择先不迁。

### 代码

- `db.js`：新增 `resolveConnectionString()`（含 `ensureSslMode`）、`resolveListenConnectionString()`、`maskUrl()`；`* .supabase.com` 主机且未写 `sslmode` 时自动补 `sslmode=require`。池参数 `max` 默认 5（`PG_POOL_MAX` 覆盖）、`idleTimeoutMillis/connectionTimeoutMillis=10s`、`keepAlive`；启动打印脱敏连接串。
- **关键坑**：Supabase 6543 是事务模式 pooler，**不支持 LISTEN/NOTIFY**，pubsub 订阅会静默失效。`resolveListenConnectionString()` 把 6543 换 5432（会话模式），`server.js` 改用它建长连接（原先是内联重复拼串）。
- 事务模式下 `pg_advisory_xact_lock` 可用（事务级，提交即释放），所以 session-create / archive 的并发保护不受影响。
- `DEPLOY.md` 相应改写：secrets 命令、优先级、两个 pooler 坑对照表、`PG_POOL_MAX`。

### 验证

- `npm test` 38/38（本地 Docker pg，无 TLS，说明补 sslmode 的判定不会误伤本地）。
- 连接串解析四场景脚本核对：默认 6543+sslmode / listen 5432 / 已带查询参数不重复追加 / PG_* 拆分串。
- 部署未执行：用户自行在终端跑（flyctl 在本沙箱无法写 `~/.fly` 配置，也需要 FLY_API_TOKEN）。

### 线上事故：`self-signed certificate in certificate chain`

- 根因是上面那条「自动补 `sslmode=require`」——**pg 8.23 起 `sslmode=require` / `prefer` / `verify-ca` 全部等价于 `verify-full`**（严格校验证书链），Supabase pooler 是自签链，于是握手失败。`pg-connection-string` 还会打 deprecation warning 提示 v3 才回到 libpq 语义。
- 修法：**不再让 pg 解析 sslmode**。`db.js` 新增 `stripSslMode()` + `sslOption()`，把 `sslmode`、`uselibpqcompat` 从串里摘掉，自己算 `ssl` 选项显式传给 `Pool` / `Client`：`require/prefer/no-verify` → `{rejectUnauthorized:false}`；`verify-full/verify-ca` → `{rejectUnauthorized:true}`；`disable` 或本地非托管主机 → `false`；未写且是 `*.supabase.com` → 加密不校验。
- 新增 `resolveClientConfig()` / `resolveListenConfig()`（`resolveListenConnectionString()` 保留为薄封装）；`pubsub.js` 的 `createPubSub` 增加 `ssl` 形参，`server.js` 改为 `createPubSub({...db.resolveListenConfig(), instanceId})`。启动日志现在会打印 TLS 模式。
- 教训：**不要用连接串参数表达 TLS 意图**，跨 pg 版本语义会漂；也不要在 grep 到一半的 `pg-connection-string` 输出上判断行为（第一轮就是把 libpq-compat 分支当成了默认分支）。

### 验证（这轮）

- Docker 起 `postgres:16 -c ssl=on` + 自签证书（/tmp/pgssl，官方镜像不再自动生成 snakeoil），先复现 `self-signed certificate`，再用新代码连同一串成功。
- 6 组 sslmode 组合的 pool/listen 判定逐条核对；TLS 下 pubsub 双实例 LISTEN/NOTIFY 实投实收。
- `npm test` 38/38。

## 数字范围 1–8 → 0–9（含两端）

- 需求：可猜数字明确为 0 到 9（含 0 和 9），并同步校验、边界判断与提示文案。
- 后端：新增 `NUMBER_MIN=0` / `NUMBER_MAX=9` 与 `parseNumber0to9()`；predict / pick / submit / confirm 四个入口统一走它。关键点：**0 不能靠 falsy 判断**——`Number(null)=0`、`Number('')=0`，所以 helper 显式拒掉 null/undefined/''/布尔，返回 `null` 表示非法，调用方一律用 `=== null` 判断。
- 连带修的真问题：额外奖品的「特殊数字」原先用 `0` 当「不启用」哨兵（`value="0"` + 归一化里 `n>=1`）。范围变 0–9 后 0 是合法特殊数字，哨兵冲突。改为：服务端只认 `null`/缺失=未启用（复用 parseNumber0to9），admin 下拉「不启用」的 value 改成 `""`，保存时空值传 null。
- 前端：players/staff 数字键盘补 0 和 9（`.numgrid` 4 列改 5 列 × 2 行）；index 单双按钮下的提示改「1/3/5/7/9」与「0/2/4/6/8」；staff 确认前的手写范围校验改 `<0 || >9`。
- i18n：三语 15 处 1-8 → 0-9，规则页 p_rule3 补「含 0 和 9」。0 按「双」判定（`n % 2 === 1 ? 单 : 双`，全链路 null 安全，0 不丢）。
- 测试：archive 用例里「9 非法」改 10；pick 新增 1 例（0/9 收、10/-1/3.5/'3x'/null/''/undefined/true 拒、提交 0 落库、锁定 0 生效）；bonus 归一化用例补 0/9 合法与 null/空串/空白/越界禁用。`npm test` 65/65。
- 文档：README（功能表、生命周期、接口表、错误码表）、docs/live-pick-sync.md、db.js 列注释同步为 0–9。
- 验证：Playwright（channel=chrome，本地 playwright 浏览器未装）截图确认 5×2 键盘与单双提示无裁切。

## 规则版本化：奖品 + 特殊数字落库、按场次锁定、对账留痕

- 需求：奖品设置与特殊数字落库并加 version；**更新规则后开始的「下一个 session」才用新规则，当前 session 的玩家不受影响**；对账表增加一列记录用了哪一版规则。
- 核心设计：把「四档奖品 + 全员额外奖励」当**一整套规则快照**，表 `rule_version(version, prizes jsonb, bonus jsonb, config_hash, source, created_by, created_at)`，append-only（复用 `archive_block_mutation()` 触发器）。一次保存 = 一版；`config_hash`（稳定序列化后 sha256）判重，内容不变不新增版本。
- 生效边界：`game_session.rule_version` 在**建场次时**由 SQL 子查询 `(SELECT max(version) FROM rule_version)` 写入（不让调用方传值：多实例下调用方缓存可能是旧的）。此后该场次所有轮次都读这一版 → 改规则对进行中场次零影响。
- 合并策略下沉到 DB 事务：`saveRuleVersion({prizes?, bonus?})` 在 advisory lock 内读最新行合并缺失的那一块。**不能用服务端内存的 latestRule 拼**——会跨实例把别人刚改的另一块静默回滚。
- 服务端：删掉 prize/bonus 的 app_config 缓存（TTL/refresh/broadcastPrizes），改为 `ruleCache: Map<version, rule>`（版本不可变，无需 TTL）+ `latestRule`；`ruleOf(session)` 按场次版本取，`buildStatePayload` 下发 `ruleVersion`；`confirm` 的 `bonusTriggered` 用锁定版本判定；保存后**不广播**（进行中场次本来就不该变），只 PUB/SUB `rule` 让各实例重拉版本表。
- 归档：`round_archive.rule_version` 在锁定那一刻写入；对账 CSV 两种口径都**追加**末列「规则版本」（空 = 版本化之前的历史行）。
- 升级：`initDb` 破例允许 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`（`game_session.rule_version`、`round_archive.rule_version`），其余「不补列」原则不变；`bootstrapRules()` 把旧 app_config 配置落成 v1 并把老场次 `pinSessionsWithoutRule()` 挂到 min(version)。
- admin：奖品页顶部显示「当前规则版本 vN · 保存后仅对之后新建的场次生效」，三语齐。
- 测试：新增 `test/rule-version.test.mjs`（5 例，含升级路径、append-only 拒改、跨轮次/跨场次版本不串、CSV 列）；按新语义重写 `prize`/`bonus` 用例（保存后当前场次不变、开新场次才生效）。`npm test` 70/70。
- 文档：README 新增 6.10「规则版本（改规则怎么生效）」，同步 6.6/6.8/6.9、接口表、7.3 CSV 列头、第 8 节表结构、第 11 节限制；DEPLOY.md 表结构同步。

### 追加：规则读取去掉 TTL / 进程内缓存，改为直查库

- 需求：规则查询不再依赖 TTL，直接从数据库拉。
- 做法：`db.SNAPSHOT_SQL` 里 `LEFT JOIN rule_version rv ON rv.version = COALESCE(gs.rule_version, (SELECT max(version) FROM rule_version))`，规则随场次快照一条 SQL 一起取出（`session.rule = {version, prizes, bonus}`）→ `buildStatePayload` 全程同步、零额外往返、天然按场次锁定版本。
- 删掉 `ruleCache` / `latestRule` / `rulesRefreshing` / `refreshRules()` / PUB-SUB `rule` 通知与 handler：规则不进进程内存就没有缓存要失效。管理端 `GET /api/prize-config|bonus-prize` 改走新增的 `db.getLatestRule()`（每次 ORDER BY version DESC LIMIT 1）；`listSessionSummaries` 也 JOIN 出有效版本，口径统一。
- 保存侧不变：仍由 DB 事务内合并 + 判重 + 分配版本号（不能用调用方手里的规则拼）。
- 测试：`rule-version.test.mjs` 新增「另一实例直接写库、无任何通知，本实例立刻读到新版」用例（配置读取 + 新建场次锁定 + state 三层验证）。`npm test` 71/71。
- 文档：README 6.10 补「规则不缓存也不存在 TTL」、测试表与用例数同步。
